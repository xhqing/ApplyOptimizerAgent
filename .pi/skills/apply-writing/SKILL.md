# 投递文案生成（apply-writing）

模板库是这个 skill 的内部参考：**产出物永远是「拿来即用的最终文字」，不是模板讲解**。用户给具体场景（岗位帖原文、招聘 JD、需求描述、谈判 / 面试进展），你按本 skill 的模板结构与红线生成——不要把模板原文丢给用户让他自己填。

接单投标与正式求职是同一条投递漏斗的两种形态（项目 2026-09-06 由 BidOptimizerAgent 更名 ApplyOptimizerAgent）：匹配度分析法、A/B 测试纪律、版本号体系两边共用；差异只在载体（申请信 / 提案 vs 打招呼 / 简历）、薪资口径（项目报价 vs 月薪 / 组合收入）与平台规则。

## 生成流程

1. **判断文案类型，读对应参考**：
   - 评论区回复 / 私信申请（接触阶段，接单侧）→ 读 `references/applications.md`
   - BOSS 打招呼 / 投递附言 / 简历定制 / 期望薪资应答 / 面试话术（求职侧）→ 读 `references/job-apply.md`
   - 正式提案 + 报价（对方已回复、方向对上了、问「怎么做 / 多少钱」）→ 读 `references/proposals.md`
   - 谈单话术（破冰 / 讨价还价 / 拒绝比稿 / 转维护）→ `references/proposals.md` 的「场景话术库」一节

2. **信息不足先要岗位原文**。匹配度分析的生命线是「岗位特有细节」——帖子 / JD 里给不出细节（痛点、场景、约束）就不动笔，先向用户要原文。这不是客套：写不出细节的申请信就是「求内推」三个字的加长版，投出去既浪费电量（电鸭）也消耗这个雇主 / HR 的唯一一次第一印象（BOSS）。

3. **按模板生成**，占位处（X、XXXX 元、X 个工作日、XX-XX K）落到岗位具体信息。价格、期望薪资、工时这类我方决策数字**不擅自填**——留占位符并标注「待定价 / 待定薪」由用户定：报价与薪资策略本身是 A/B 测试变量（`docs/ab-test.md`），且底价 / 底薪属敏感信息。

4. **生成后逐条自检红线**（细则在对应 reference）：
   - 有岗位特有细节的复述（用自己的话转述帖子 / JD 里的痛点 / 场景 / 约束，不是照抄标题）；
   - 能力对照每条带证据（交付物、可演示小样、仓库链接），没有「精通 XXX」式自评；
   - 接触阶段（评论 / 首封私信 / 首条打招呼）不出现报价与期望薪资——报价是谈单阶段的动作，谈薪是面试后期的动作；
   - 提案里远程信任三件套齐全：响应节奏（在线时段、回复时效）、过程可见（阶段同步 / 演示）、退出机制（试用期 / 分阶段付款）；
   - 期望薪资口径分渠道：坐班岗按全职月薪口径，远程岗按组合收入逻辑（CLAUDE.md 2026-09-05 规则），不混用。

5. **输出格式**：最终文字放代码块方便直接复制；末尾标注本次使用的模板版本号（如 `L-评论-v1.0`、`T-自动化-v1.0`、`B-打招呼-v1.0`）——投出后记台账 `proposal_version` 字段要用。

## 文案被采纳投出后

提醒用户按记录 SOP 的触发器 2 当场记台账（`docs/ledger.csv`）：投出那一刻样本进入转化率分母候选，漏记 = 分母失真。完整口径与触发器速查表见 `docs/bidding-record-sop.md`。

## 模板迭代纪律

- 模板改版的唯一合法依据是 A/B 测试结论（`docs/ab-test.md`）与输单 / 复盘结论；改版必须升版本号并写入对应 reference 文末的迭代日志，不许凭单次感觉改模板。
- 版本号体系：申请信 `L-评论-v?` / `L-私信-v?`；提案 `T-AI应用-v?` / `T-自动化-v?` / `T-轻量开发-v?`（类型段与台账 `job_type` 字段一一对应）；求职侧打招呼 `B-打招呼-v?`、简历 `J-简历-v?`（薪资与面试话术暂随打招呼 / 简历版本走，不单设版本）。
- 沿革：本 skill 原名 `bid-writing`（投标文案生成，电鸭接单单场景），2026-09-07 随项目更名改为 `apply-writing` 并扩展求职侧——「投单」与「找工作」合流为同一条投递漏斗。
