# 投标文案生成（bid-writing）

模板库是这个 skill 的内部参考：**产出物永远是「拿来即用的最终文字」，不是模板讲解**。用户给具体场景（岗位帖原文、需求描述、谈判进展），你按本 skill 的模板结构与红线生成——不要把模板原文丢给用户让他自己填。

## 生成流程

1. **判断文案类型，读对应参考**：
   - 评论区回复 / 私信申请（接触阶段）→ 读 `references/applications.md`
   - 正式提案 + 报价（对方已回复、方向对上了、问「怎么做 / 多少钱」）→ 读 `references/proposals.md`
   - 谈单话术（破冰 / 讨价还价 / 拒绝比稿 / 转维护）→ `references/proposals.md` 的「场景话术库」一节

2. **信息不足先要帖子原文**。匹配度分析的生命线是「岗位特有细节」——帖子里给不出细节（痛点、场景、约束）就不动笔，先向用户要原文。这不是客套：写不出细节的申请信就是「求内推」三个字的加长版，投出去既浪费电量也消耗这个雇主的唯一一次第一印象。

3. **按模板生成**，占位处（X、XXXX 元、X 个工作日）落到岗位具体信息。价格与工时这类我方决策数字**不擅自填**——留占位符并标注「待定价」由用户定：报价策略本身是 A/B 测试变量（`docs/ab-test.md`），且底价属敏感信息。

4. **生成后逐条自检红线**（细则在 `references/applications.md`）：
   - 有岗位特有细节的复述（用自己的话转述帖子里的痛点 / 场景 / 约束，不是照抄标题）；
   - 能力对照每条带证据（交付物、可演示小样、仓库链接），没有「精通 XXX」式自评；
   - 接触阶段（评论 / 首封私信）不出现报价——报价是谈单阶段的动作；
   - 提案里远程信任三件套齐全：响应节奏（在线时段、回复时效）、过程可见（阶段同步 / 演示）、退出机制（试用期 / 分阶段付款）。

5. **输出格式**：最终文字放代码块方便直接复制；末尾标注本次使用的模板版本号（如 `L-评论-v1.0`、`T-自动化-v1.0`）——投出后记台账 `proposal_version` 字段要用。

## 文案被采纳投出后

提醒用户按记录 SOP 的触发器 2 当场记台账（`docs/ledger.csv`）：投出那一刻样本进入转化率分母候选，漏记 = 分母失真。完整口径与触发器速查表见 `docs/bidding-record-sop.md`。

## 模板迭代纪律

- 模板改版的唯一合法依据是 A/B 测试结论（`docs/ab-test.md`）与输单复盘结论；改版必须升版本号并写入对应 reference 文末的迭代日志，不许凭单次感觉改模板。
- 版本号体系：申请信 `L-评论-v?` / `L-私信-v?`；提案 `T-AI应用-v?` / `T-自动化-v?` / `T-轻量开发-v?`（类型段与台账 `job_type` 字段一一对应）。
